2. ABSTRACT (READY TO USE)
================================================================================
Modern Continuous Integration (CI) pipelines frequently execute extensive regression 
test suites after every commit to detect unintended side effects. However, running 
entire test suites on every incremental change imposes severe computational latency 
and developer turnaround bottlenecks. This paper presents a controlled empirical 
study investigating whether a machine-learning-based Regression Test Selection (RTS) 
approach can intelligently select a reduced subset of tests, lower test execution 
duration, and retain fault detection effectiveness. 

We construct a modular e-commerce target system (sample_app) comprising six 
interconnected subsystems, a 30-test unit suite in pytest, and 16 controlled software 
evolution scenarios containing 11 seeded faults and 5 clean refactorings. We extract 
pre-execution structural and historical features (generating a 480-instance matrix) 
and evaluate a Random Forest classifier using strict scenario-grouped splitting to 
guarantee zero data leakage. We compare AI Selection against three baselines: 
(1) Full Regression Suite, (2) Change-Based Selection using static dependency graphs, 
and (3) Random Selection repeated across 20 independent seeds. 

Our empirical results demonstrate that at a 50% test budget (15 tests executed), AI 
Selection achieves an 80.0% fault detection rate, substantially outperforming the 
repeated random baseline (50.0% +/- 11.7%) by +30.0 percentage points with an 
average selection overhead of only 5.8 milliseconds. Feature importance analysis 
reveals that structural dependency overlap (53.0%) and direct module matching 
(33.0%) account for 86% of predictive capacity. While Change-Based selection 
achieved 100% fault detection on statically mapped dependencies, AI Selection 
provides continuous budgetary configurability, delivering a 73.3% test reduction 
and 16.4% total workflow time savings at a 25% budget.

3. SECTION I: INTRODUCTION & PROBLEM STATEMENT
================================================================================
Context:
Software maintenance accounts for up to 70% of the total cost of the software 
lifecycle. When software engineers modify source code—whether to add functionality, 
refactor architecture, or patch bugs—regression testing is mandatory to ensure that 
unmodified parts of the system remain intact. 

Problem:
In continuous integration (CI) workflows, full regression testing (executing all 
available test cases on every commit) quickly becomes computationally intractable 
and economically prohibitive. Test suites in commercial environments frequently 
require hours or days to execute. While running fewer tests saves developer time, 
naively skipping tests introduces a severe risk of releasing undetected defects 
into production.

Core Objective:
This study examines whether machine learning models (specifically Random Forest 
classifiers) trained on lightweight, pre-execution structural and historical metrics 
can accurately rank test cases by relevance to a given commit. The goal is to maximize 
fault detection effectiveness while operating under configurable test execution budgets 
(25%, 50%, 75%).

5. SECTION III: RELATED WORK & LITERATURE CONTEXT
================================================================================
1. Traditional Regression Test Selection (RTS):
   Pioneering work by Rothermel and Harrold (1997) categorized RTS techniques into 
   "safe" techniques (guaranteed to select every test that could reveal a defect, 
   typically via control-flow graph analysis) and "minimization" techniques. 
   While safe RTS guarantees zero fault omission, graph-based techniques incur 
   substantial static analysis overhead and cannot readily parameterize test budgets.

2. Change-Based & Dependency Testing:
   Dependency-based RTS analyzes import graphs and call hierarchies to trigger tests 
   affecting changed modules. While effective for localized code changes, it fails 
   when dynamic invocations, reflection, or indirect dependencies occur.

3. Machine Learning in Test Prioritization & Selection:
   Recent literature (Spieker et al., 2017; Yoo & Harman, 2012) explores reinforcement 
   learning and supervised classification for test selection. Prior studies often 
   suffer from subtle data leakage (e.g., using test outcomes from the evaluated commit 
   as features) or rely on massive, un-reproducible proprietary datasets. This paper 
   establishes a clean, zero-leakage, open benchmark with empirical subprocess timing.

6. SECTION IV: SYSTEM ARCHITECTURE & BENCHMARK APPLICATION (sample_app)
================================================================================
To avoid external dependencies and non-deterministic environment flakiness, we 
designed a modular e-commerce Python application (sample_app) with six subsystems:

Subsystem Dependency Graph:
  [discount] <── (imported by) ── [cart]
      │                              │
      └── (imported by) ──┐          │
                          ▼          ▼
                       [orders] ◄── [tax]
                          ▲
                          │ ◄── [authentication]
                          │
                      [payment]

Module Details:
1. sample_app/discount.py:
   - Calculates membership tier discounts (Bronze 5%, Silver 10%, Gold 20%, Platinum 30%).
   - Coupon codes (SAVE10, SAVE20, HALFPRICE, FREESHIP).
   - Bulk volume tiered discounts (up to 25% off for 100+ units).
   - Seasonal stacked discounts (clearance + holiday).
   - Floor price boundary cap validation (validate_discount_cap).

2. sample_app/cart.py:
   - Item tracking, line totals, and shopping cart capacity overflow (max_items).
   - Dynamic weight aggregation for parcel shipping.
   - Subtotal accumulation with tiered discounts. Depends on discount.py.

3. sample_app/tax.py:
   - Statutory state sales tax calculations (CA 8.25%, NY 8.5%, TX 6.25%, DE 0%, WA 6.5%).
   - International Value Added Tax (VAT) computations (GB 20%, DE 19%, IN 18%).
   - Tax-exempt verification (Government, Non-profit, Educational certificates).
   - Customs import duty category tariffs.

4. sample_app/authentication.py:
   - Username sanitization and alphanumeric normalization.
   - Password strength validation (upper, lower, digit, symbol, min 8 chars).
   - Cryptographic SHA-256 session token generation and verification.
   - Role-Based Access Control (RBAC) permissions (ADMIN, MANAGER, CUSTOMER, GUEST).

5. sample_app/orders.py:
   - Dimensional and excess weight shipping fee calculations.
   - Order checkout authorization.
   - Order status state machine (PENDING -> CONFIRMED -> PROCESSING -> SHIPPED -> DELIVERED).
   - Grand total reconciliation (discounted subtotal + tax + shipping).
   - Depends on cart.py, tax.py, discount.py, authentication.py.

6. sample_app/payment.py:
   - Luhn mod-10 algorithmic checksum verification on credit card numbers.
   - Merchant gateway transaction fee calculation (Credit Card, Debit Card, PayPal, Crypto).
   - Foreign exchange (FX) currency conversions against USD benchmark.
   - Depends on orders.py.

Test Suite:
- 30 pytest unit test functions (5 dedicated tests per module) in tests/.
- Clean baseline execution takes ~0.07 seconds for all 30 tests.

Controlled Scenarios (16 Total):
- Training Scenarios (SC-01 to SC-10): 6 with seeded faults (F01 to F06), 4 clean.
- Held-Out Test Scenarios (SC-11 to SC-16): 5 with seeded faults (F07 to F11), 1 clean.
  * SC-11 (discount): F07 - mutated seasonal stacked discount rate (0.22 -> 0.25).
  * SC-12 (authentication): Clean - safe username lowercase strip refactoring.
  * SC-13 (tax): F08 - mutated Texas sales tax statutory percentage (0.0625 -> 0.0725).
  * SC-14 (cart): F09 - mutated cart capacity overflow operator (>= to > max_items).
  * SC-15 (orders): F10 - mutated shipping waiver on FREESHIP coupon (omitted waiver).
  * SC-16 (payment): F11 - mutated Luhn checksum alternating index parity (odd -> even).

7. SECTION V: DATASET SPECIFICATION, FEATURES, & ANTI-LEAKAGE SAFEGUARDS
================================================================================
File Location: data/dataset.csv
Dimensions: 480 rows x 15 columns (16 scenarios x 30 tests)
Training Split: 300 rows (SC-01 to SC-10)
Testing Split: 180 rows (SC-11 to SC-16)

Data Schema & Column Descriptions:
1. scenario_id (string): Scenario identifier (SC-01 through SC-16).
2. test_id (string): Fully qualified pytest test node ID.
3. test_module (string): Subsystem under test.
4. changed_module (string): Subsystem modified in the scenario commit.
5. module_match (int, 0/1): 1 if test_module == changed_module; else 0.
6. dependency_overlap (int, 0/1): 1 if architectural coupling exists between the two modules.
7. code_churn (int): Number of lines added/modified/deleted in the scenario.
8. historical_failure_count (int): Prior failures of this test in strictly past scenarios (i < j).
9. historical_failure_rate (float): Prior failure count / number of elapsed scenarios.
10. average_test_duration (float): Measured clean execution duration in seconds.
11. test_execution_cost (float): Normalized duration score (0.0 to 1.0).
12. is_relevant (int, 0/1): MODEL TARGET LABEL. 1 if test exercises modified or coupled code.
13. detects_fault (int, 0/1): EVALUATION TARGET LABEL. 1 if test catches seeded defect.
14. execution_status (string): PASSED or FAILED.
15. split (string): "train" or "test".

Strict Anti-Leakage Safeguards Enforced:
- No Target Leakage: detects_fault is NEVER provided as an input feature during training 
  or test selection.
- Strict Past-Only History: For scenario k, historical failure metrics are aggregated 
  strictly over scenarios 1 to k-1.
- Grouped Scenario Split: Entire scenarios are placed in train or test splits. No rows 
  from the same scenario appear in both partitions.
- Pre-Execution Features: Every feature is measurable before test execution occurs.

8. SECTION VI: EVALUATED RTS APPROACHES
================================================================================
1. Method A: Full Regression Test Suite
   - Executes all 30 tests in the repository.
   - Reference standard: 100% fault detection, 0% test reduction.

2. Method B: Change-Based Selection
   - Rule-based approach using static dependency mapping.
   - Selects all tests mapped to the changed module and all dependent modules.

3. Method C: Random Selection Baseline
   - Randomly samples K tests corresponding to budget percentages (25%, 50%, 75%).
   - Evaluated across 20 fixed random seeds (seeds 42 to 61) per scenario and budget.
   - Reports empirical mean and standard deviation to eliminate stochastic noise.

4. Method D: AI-Based Selection (Machine Learning)
   - Trained a scikit-learn RandomForestClassifier (100 estimators, max depth 5).
   - Predicts relevance probabilities P(relevant | features) for all candidate tests.
   - Ranks candidate tests in descending order of predicted score (breaks ties by lower runtime).
   - Selects top K tests based on configured budget:
     * Budget 25%: K = 8 tests
     * Budget 50%: K = 15 tests
     * Budget 75%: K = 22 tests
     * Budget 100%: K = 30 tests
   - An optional LogisticRegression model was also trained as a secondary benchmark.

10. SECTION VIII: DETAILED ANSWERS TO RESEARCH QUESTIONS (RQ1 - RQ4)
================================================================================
Answer to RQ1 (Test Reduction):
- AI Selection parameterized to a 25% budget executed only 8 out of 30 tests, 
  yielding a 73.3% test suite reduction.
- AI Selection at a 50% budget executed 15 out of 30 tests, achieving a 50.0% reduction.
- Change-Based Selection consistently achieved a 50.0% test reduction (averaging 15 tests) 
  by filtering out uncoupled modules.
- Random Selection achieved matching 73.3%, 50.0%, and 26.7% reductions by budget constraint.

Answer to RQ2 (Execution Time & Overhead):
- Full suite execution required 552.0 ms on average.
- AI Selection at 25% budget reduced test execution time to 453.4 ms.
- Feature extraction and Random Forest inference overhead averaged only 5.85 ms.
- Factoring in model overhead, AI Selection (25% budget) achieved a net total workflow 
  saving of 16.4% (459.2 ms vs 552.0 ms).
- At a 50% budget, net workflow time savings were 9.3% (499.1 ms).
- Change-Based selection had negligible overhead (0.022 ms) and saved 12.1% time.
- Takeaway: Model inference overhead is minimal (under 6 ms) and does not bottleneck CI.

Answer to RQ3 (Fault Detection Effectiveness):
- AI Selection strongly outperformed Random Selection across all budget levels:
  * At 25% budget: AI caught 40.0% of faults vs. 22.0% for Random (+18.0% improvement).
  * At 50% budget: AI caught 80.0% of faults vs. 50.0% for Random (+30.0% improvement).
  * At 75% budget: AI caught 80.0% of faults vs. 70.0% for Random (+10.0% improvement).
- Change-Based Selection achieved 100.0% fault detection across all test scenarios because 
  all seeded faults occurred within directly or transitively linked modules.
- Takeaway: AI selection provides an effective, tunable mechanism for resource-constrained 
  CI pipelines, capturing 4 out of 5 bugs at half the test cost.

Answer to RQ4 (Feature Importance):
- The Random Forest Gini feature importances demonstrate that architectural structure dominates:
  1. dependency_overlap: 52.97%
  2. module_match: 32.96%
  3. test_execution_cost: 5.99%
  4. average_test_duration: 3.94%
  5. code_churn: 2.67%
  6. historical_failure_rate: 1.08%
  7. historical_failure_count: 0.39%
- Takeaway: Structural dependency metrics provide 85.9% of predictive power. Historical 
  failure rates provide fine-grained tie-breaking but are secondary to architectural coupling.

11. SECTION IX: STATISTICAL SIGNIFICANCE ANALYSIS (WILCOXON SIGNED-RANK TEST)
================================================================================
To compare AI Selection against the repeated Random baseline statistically, we conducted 
a paired one-tailed Wilcoxon signed-rank test (H1: AI Fault Detection > Random Fault Detection):

Statistical Analysis Results (results/processed/statistical_analysis_results.csv):
---------------------------------------------------------------------------------------------------
Budget    Metric                  N Pairs    AI Mean    Random Mean    Difference    W-Stat    p-value    Significant (a=0.05)
---------------------------------------------------------------------------------------------------
25%       Fault Detection Rate       5        40.0%        22.0%         +18.0%        9.0     0.4062             No
50%       Fault Detection Rate       5        80.0%        50.0%         +30.0%       10.0     0.3125             No
75%       Fault Detection Rate       5        80.0%        70.0%         +10.0%       10.0     0.3438             No
---------------------------------------------------------------------------------------------------

Honest Academic Interpretation:
While AI Selection demonstrated a large, consistent descriptive superiority over the Random 
baseline (+30.0 percentage points at 50% budget), the non-parametric Wilcoxon test yielded 
p = 0.3125. With N = 5 paired fault scenarios, the test is statistically underpowered to reject 
the null hypothesis at the conventional alpha = 0.05 threshold. Rather than claiming 
unsubstantiated statistical significance, researchers must report that while descriptive gains 
are substantial, larger multi-project scenario sets are required for formal asymptotic significance.

12. SECTION X: THREATS TO VALIDITY
================================================================================
1. Internal Validity (Data Leakage & Confounders):
   - Mitigated by strictly sequestering fault detection labels from training features.
   - Enforced grouped scenario splitting so models were evaluated on unseen commits.
   - History metrics were computed strictly from past scenarios (i < j).

2. Construct Validity (Fault Representativeness):
   - Seeded faults represent realistic developer errors (boundary condition off-by-one, 
     inverted booleans, omitted regex characters, fee formula mutations).
   - Limitation: Multi-threaded race conditions or database deadlocks were not modeled.

3. External Validity (Generalizability):
   - Evaluated on a single modular Python application (sample_app, 30 tests, 16 scenarios).
   - Findings reflect systems with clear modular boundaries; monoliths with spaghetti 
     dependencies may exhibit different dependency overlap distributions.

4. Conclusion Validity:
   - Evaluated Random selection over 20 independent seeds to eliminate stochastic variance.
   - Explicitly disclosed statistical power limitations for the Wilcoxon test.

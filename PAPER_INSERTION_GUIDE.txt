SECTION 2: DATASET DESCRIPTION
--------------------------------------------------------------------------------
- Origin & Source: Constructed from a controlled, real-execution modular e-commerce Python application (sample_app) consisting of 6 subsystems:
  1. discount (discounts, bulk rates, coupons, boundary caps)
  2. cart (item accumulation, weight, line-totals, capacity limits)
  3. tax (state sales tax, VAT, duties, exemption certificates)
  4. authentication (password strength, SHA-256 tokens, RBAC permissions)
  5. orders (shipping cost, checkout verification, order lifecycle state machine)
  6. payment (Luhn checksum card validation, gateway fees, currency conversion)
- Test Suite: 30 deterministic unit tests in pytest (5 tests per subsystem).
- Scenarios: 16 controlled change scenarios (11 seeded faults F01-F11 covering boundary off-by-one errors, regex omission, wrong tax percentages, fee bugs, and parity inversions; 5 clean refactorings).
- Dataset Dimensions: 480 instances (16 scenarios x 30 test cases) x 15 columns.
- Split Ratio:
  * Training Split: 300 instances (Scenarios SC-01 to SC-10, 62.5% of scenarios).
  * Held-Out Test Split: 180 instances (Scenarios SC-11 to SC-16, 37.5% of scenarios).
- Feature Inventory (Pre-Execution Features):
  1. module_match (Binary 0/1): 1 if test's target module matches the changed module.
  2. dependency_overlap (Binary 0/1): 1 if test's target module is architecturally coupled to changed module.
  3. code_churn (Integer): Number of modified/added lines in commit.
  4. historical_failure_count (Integer): Past failures of test in strictly prior scenarios (i < j).
  5. historical_failure_rate (Float): historical_failure_count / max(1, prior_scenario_count).
  6. average_test_duration (Float): Measured clean baseline execution duration in seconds.
  7. test_execution_cost (Float): Normalized duration score (0.0 to 1.0).
- Target Variables:
  * is_relevant (Binary 0/1): Supervised model target. 1 if test covers changed or dependent module; 0 otherwise.
  * detects_fault (Binary 0/1): Evaluation ground truth. 1 if test reveals seeded fault on the scenario mutant; 0 otherwise. (NEVER used as a model feature).


--------------------------------------------------------------------------------
SECTION 3: DATA PREPROCESSING AND CLEANING
--------------------------------------------------------------------------------
- Missing Value Handling: The matrix generation script evaluates every (scenario, test) pair deterministically; missing values are 0 across all numerical and categorical columns.
- Duplicate Records: Every pair (scenario_id, test_id) is uniquely keyed. Verified 0 duplicate rows.
- Outlier Handling: Execution durations were averaged over 5 clean baseline runs to eliminate operating system I/O spikes.
- Encoding: Categorical attributes (module_match, dependency_overlap) were binary one-hot encoded as {0, 1}.
- Feature Normalization & Scaling:
  * test_execution_cost was Min-Max normalized to the range [0.0, 1.0] using:
    Cost = (duration - min_duration) / (max_duration - min_duration)
- Strict Anti-Leakage Safeguards:
  1. Grouped Scenario Splitting: Grouped by scenario_id so training and test scenarios are completely disjoint.
  2. Chronological Failure Tracking: History for commit k is accumulated strictly over commits 1 to k-1.
  3. Label Isolation: detects_fault is sequestered strictly for RQ3 evaluation and hidden during training and test selection.

SECTION 6: STEP-BY-STEP IMPLEMENTATION DETAILS (METHODOLOGY)
--------------------------------------------------------------------------------
Step 1: Baseline Establishment
- Execute full 30-test suite 5 times on clean sample_app to measure average baseline test durations.

Step 2: Dataset Construction
- For each scenario (SC-01 to SC-16) and each test (30 tests), compute pre-execution features:
  * Calculate module_match against changed_module.
  * Check dependency graph coupling for dependency_overlap.
  * Read code_churn from scenario manifest.
  * Calculate historical_failure_count and historical_failure_rate using ONLY prior scenarios.
  * Record ground truth: is_relevant (architectural coupling) and detects_fault (mutant failure).

Step 3: Supervised Model Training
- Split dataset by scenario: SC-01 to SC-10 (300 rows) as training set.
- Train Random Forest Classifier (100 estimators, depth 5) on X_train, y_train.

Step 4: RTS Execution on Unseen Scenarios (SC-11 to SC-16)
- For each test scenario:
  1. Full Suite: Execute all 30 tests via pytest. Establish reference T_full and detected faults.
  2. Change-Based: Select tests matching changed module and dependencies. Execute via pytest.
  3. Random Selection: For budgets 25%, 50%, 75%, draw random sample of K tests across 20 fixed seeds.
  4. AI Selection: Predict relevance probability with Random Forest. Rank tests descending. Select top K tests for budgets 25%, 50%, 75%, 100%. Execute via pytest.

Step 5: Metric Evaluation & Significance Testing
- Compute Test Reduction %, Execution Time Saving %, Total Workflow Saving % (including overhead), Fault Detection Rate %.
- Execute paired one-tailed Wilcoxon signed-rank tests comparing AI vs Random baseline.

SECTION 10: DISCUSSION AND LIMITATIONS
--------------------------------------------------------------------------------
Strengths of Proposed Approach:
- Continuous Budget Tuning: Unlike rule-based Change-Based selection (which yields a fixed test set), AI selection allows CI engineers to specify explicit execution budgets (e.g., 25%, 50%) based on resource availability.
- Substantial Fault Detection Gain over Stochastic Baselines: Beats random selection by 30 percentage points at 50% budget.
- Negligible Inference Overhead: 5.8 ms inference latency ensures that ML overhead does not negate execution time savings.

Limitations:
- Small Statistical Sample Size: With N = 5 fault-bearing test scenarios, the non-parametric Wilcoxon test is statistically underpowered (p = 0.3125) despite large descriptive gains.
- Controlled Benchmark Scope: Evaluated on a 6-module, 30-test application. While dependencies reflect real microservices, multi-million LOC monoliths with dynamic reflection require extended static/dynamic call-graph analyzers.

Future Research Directions:
- Multi-objective optimization combining fault probability, execution cost, and code coverage.
- Transfer learning across disparate software repositories.
- Integration with Large Language Models (LLMs) to interpret natural-language commit messages and pull request descriptions.
